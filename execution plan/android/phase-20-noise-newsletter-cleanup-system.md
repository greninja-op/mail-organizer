# Phase 20 — Noise, Newsletter & Cleanup System

## Mission

Implement Mail Organizer's **Noise, Newsletter & Cleanup System**.

The goal is to help users understand and control low-value email without turning Mail Organizer into an aggressive automatic deletion system.

This phase must provide:

- newsletter identification
- notification/noise identification
- low-value email intelligence
- sender/domain noise controls
- newsletter management
- cleanup recommendations
- safe bulk-review workflows
- explainable cleanup suggestions
- account-scoped cleanup rules
- strong protection against accidental destructive actions

The central principle is:

> **Identify and organize first. Recommend cleanup second. Execute destructive actions only with explicit user confirmation and only through the appropriate future Gmail-write architecture.**

Mail Organizer must never equate:

```text
low value
=
safe to delete
```

or:

```text
newsletter
=
unwanted
```

# 5. Core Product Principle

Noise management is an intelligence layer, not a deletion engine.

The architecture should be:

```text
Normalized Email
      ↓
Existing Classification
      ↓
Existing Sender/Company Intelligence
      ↓
Existing User Rules/Corrections
      ↓
Noise & Newsletter Analysis
      ↓
Cleanup Recommendation
      ↓
User Review
      ↓
Future explicit Gmail action
```

Do not create a second competing category classifier.

---

# 6. Distinguish the Concepts

Do not collapse these concepts:

### Newsletter

Recurring informational/promotional email that is typically subscription-based.

### Notification

Automated message generated by a service or system.

### Promotional Email

Commercial marketing communication.

### Noise

Email with low practical value for the user based on available evidence.

### Low Value

An intelligence judgment, not a destructive-action permission.

### Cleanup Candidate

A message/thread that meets defined criteria for review.

### Safe Cleanup

A user-confirmed operation whose consequences are clearly communicated.

These concepts must remain separate in the domain model.

# 8. Newsletter Intelligence

Detect newsletter-like messages using deterministic signals.

Possible signals:

- unsubscribe information
- `List-Unsubscribe` headers
- recurring sender/domain
- repeated subject patterns
- bulk-like sender behavior
- newsletter-style content
- promotional/informational patterns
- Gmail category
- sender/company behavior
- user corrections/rules

Do not rely on one signal alone.

---

# 9. Newsletter Confidence

Newsletter detection must produce:

- result
- confidence
- explanation
- version

Example:

```text
Newsletter
Confidence: High

Why:
• Unsubscribe header detected
• Sender sends repeatedly
• Newsletter-style formatting
```

Do not expose meaningless numerical confidence unless it is useful.

---

# 10. Unsubscribe Signals

Treat unsubscribe information carefully.

Possible sources:

- `List-Unsubscribe`
- `List-Unsubscribe-Post`
- body text
- known subscription patterns

Do not automatically visit unsubscribe URLs.

Do not automatically click links.

Do not automatically send unsubscribe requests.

---

# 11. Unsubscribe Safety

Unsubscribe links are untrusted email content.

They may:

- track users
- redirect
- contain malicious URLs
- require authentication
- perform unwanted actions

The application must not automatically invoke them.

If an unsubscribe option is later presented, make it explicitly user initiated.

# 16. Notification Intelligence

Detect automated notifications using deterministic signals.

Possible signals:

- sender/domain
- known service patterns
- subject patterns
- recurring messages
- machine-generated headers where available
- Gmail category
- content structure
- unsubscribe information
- existing sender/company intelligence

Do not hard-code an enormous list of companies.

---

# 17. Noise Intelligence

Noise detection should consider multiple signals.

Potential signals:

```text
newsletter
notification
promotion
recurring low-value sender
low user interaction
duplicate/repeated content
non-actionable informational email
```

However:

> Low interaction must never automatically mean unwanted.

Do not use simplistic:

```text
=
delete
```

logic.

---

# 18. User Interaction as a Weak Signal

If interaction data is available locally, it may be used conservatively.

Examples:

- read/unread
- recurring sender
- user corrections

Do not infer user preferences from sensitive behavior unnecessarily.

Do not build invasive behavioral profiling.

---

# 19. Low-Value Detection

A low-value recommendation should be explainable.

Example:

```text
Likely low value because:
• automated notification
• recurring sender
• no action requested
```

Never show:

> "We know you don't care about this."

Use uncertainty-aware language.

# 26. Thread vs Message Semantics

Be careful with thread-level cleanup.

One message in a thread may be low value while another is important.

Do not automatically treat an entire thread as disposable based on one message.

Where thread-level actions are considered, explain the scope.

- career email
- education email
- action-required email
- important email

should receive stronger protection from cleanup recommendations.
